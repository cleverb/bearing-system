# ADR-0014: Recovery telemetry is durable run-state; MCP Apps project it

* **Date:** 2026-08-23
* **Deciders:** BEARING maintainers
* **Tickets:**

## Context and Problem Statement

Decision recovery is agent-executed archaeology (ADR-0008). Operators want a
live tally of that work in an MCP App. Routing every scan increment through
the model as a tool call would make the agent loop the animation layer: extra
JSON-RPC turns, extra model-visible context, and a UI that dies if chat stalls.

MCP Apps can poll `resources/read` from the View. Forwarding
`resources/subscribe` into a View is not a reliable host capability.

## Decision Drivers

* Run state belongs in `.bearing/` (ADR-0002); the plugin tree stays read-only.
* The model must see semantic checkpoints, not file-by-file animation.
* A closed chat or a host without MCP Apps must not erase recovery progress.
* Confidence and ETA must not pretend precision the stages do not have.

## Considered Options

1. Agent calls `report_recovery` every few seconds; the App renders each tool result.
2. App polls a file the agent overwrites, with no MCP resource and no durable schema.
3. Agent writes `.bearing/runs/recovery/<run-id>/status.json` (snapshot) and
   `events.jsonl` (append-only). The Recovery App polls a read-only MCP resource
   that projects that state. Checkpoint tools exist only for start, complete,
   budget constraint, and failure. After complete, `list_reviewable` opens Review.

## Decision Outcome

Chosen option: **3**.

* Canonical live telemetry is workspace run-state, not a conversation.
* Event-driven writes; time-driven UI reads (~5s while `status` is `running`).
* ETA is per-stage rates plus remaining-stage ranges, with an explicit
  confidence. Never `locations_done / total * remaining_stages`.
* Hosts that cannot render MCP Apps receive compact JSON fallback. Disposition
  and recovery CLI remain available without the App.
* The Review App is a separate resource (`ui://bearing/reviewable-queue`). The
  Recovery App must not call `list_reviewable` itself.

## Consequences

* `bearing recovery-status` is a mechanical writer, not an extractor pipeline.
* Replacing App polling with host-forwarded `resources/subscribe` later does
  not change the status file contract.
* Another agent can inspect the same run after the original chat ends.

## Deletion test

If this Contract is removed, recovery progress either lives only in chat (lost
on close, invisible to a second agent) or is animated by per-file model tool
calls (the model becomes the heartbeat). Both contradict ADR-0002 and ADR-0008.
