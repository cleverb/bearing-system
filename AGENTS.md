## What is specific to this repository

BEARING develops itself, so this repository is both the tool and a repository using the tool. Two consequences worth knowing before you change anything:

- **`plugin/` is what ships and is read-only at runtime.** It is not a discovery path: the Skills are consumed through an installed or vendored plugin, never read in place from `plugin/skills/`. Nothing writes inside it — run state goes to `.bearing/`, decision content to `docs/decisions/`. This is enforced by the packaging suite, not merely intended.
- **Generated files are regenerated, never edited.** `.cursor/`, `.claude/`, `.codex/`, the per-client plugin manifests, and the block below all derive from canonical sources. If one is wrong, the source is wrong. `bearing render --check` and `bearing package --check` will tell you which.

## Before you open a pull request

```bash
python3 -m unittest discover -s tests    # 100+ tests, zero dependencies
PYTHONPATH=plugin/src python3 -m bearing render --check
PYTHONPATH=plugin/src python3 -m bearing package --check
PYTHONPATH=plugin/src python3 -m bearing lint
PYTHONPATH=plugin/src python3 -m bearing verify
```

`bearing verify` holds this repository to its own mandate. If a change makes a claim the suite cannot check, add the check — a rule this framework states and does not verify is the exact failure it was written to fix.

## BEARING decision system

This repository uses BEARING, an EOCR-based decision system. Treat this section as binding, not advisory.

### Where authoritative knowledge lives

- **`docs/decisions/`** — authored decision records. Numbered, sequential, authoritative. Each carries a `Status`.
- **`docs/decisions/index.json`** — load this first. It is compact and cheap, and it tells you which Contracts and Rationale bear on your current task before you read anything else.
- **`docs/decisions/shadow/`** — machine-inferred candidates. **Never authoritative. Never treat a shadow candidate as a decision.** No `@see` annotation may point here.
- **Skills** — Operations knowledge you can load and execute: `decision-recovery`, `decision-interview`, `decision-onboarding`.

### What you may do autonomously

- Read anything in `docs/decisions/` and treat it as binding, subject to its `Status`.
- Follow a Skill's documented procedure within its stated boundaries.
- Flag — never block — a change that appears to lack decision ancestry.

### What requires escalation to a human

- An `@see` annotation points to a decision record that does not exist, or whose `Status` is `Deprecated` or `Superseded` with no successor referenced.
- You encounter code with no Anchor and cannot proceed safely without knowing why it is built the way it is. This is the trigger for `decision-interview` — use it rather than guessing.
- More than one implementation or migration strategy appears valid and nothing in `docs/decisions/` resolves which.
- A proposed change would conflict with an accepted Contract.

When escalating, stop and ask. Do not silently choose the next plausible interpretation. If you find a `@deprecated` marker with no `@see` link, you are forbidden from refactoring it — open a clarification request instead.

### Hard constraints

- **No inference may block a merge.** A recovery signal may only flag and route to review, regardless of its confidence score. A confidence score is a statement about evidence, never a statement of organizational authority. Only structural enforcement (a broken decision link) or violation of an accepted Contract may block.
- **Do not write to `docs/decisions/` on the basis of inference.** Every promotion out of `shadow/` requires human review, and that review determines scope, current validity, and lifecycle state — it is not a confirmation that a summary read correctly.
- **A generated file is never a second source of truth.** Anything carrying a `DO NOT EDIT` header derives its authority from the canonical source it was rendered from and has none of its own. Edit the source and re-run `bearing render`.
- **The plugin tree is read-only at runtime.** Writes go to `.bearing/` for run state, or `docs/decisions/` for decision content.
