# decision-onboarding

Primes a repository for BEARING. Not a new mechanism — a bounded, sequenced composition of `decision-recovery` and `decision-interview`, run once per repository, that produces one reviewable branch and a frozen baseline to test it against.

Run once, explicitly. Never automatic, never re-run silently on an already-onboarded repository.

```bash
bearing onboard start                 # default profile: pilot
bearing onboard start --profile audit # measure first, promote nothing
```

## Install is not step one

This Skill assumes BEARING is already installed and the workspace is already bootstrapped. Those are two separate layers that onboarding does not own:

1. **Distribution** — the `bearing` plugin is installed from a marketplace, once per user or per organization. Nothing is committed to the target repository.
2. **Bootstrap** — `bearing init` writes `.bearing/config.json` and scaffolds the decisions directory, after detecting whatever convention the repository already uses.
3. **Operation** — this Skill, steps 0 through 6.

Step 0a Preflight verifies the first two rather than assuming them, and fails with the command to run rather than proceeding on a broken foundation. That gap — a repository with no `.agents/` tree at all, where onboarding was documented as starting from an already-installed state — is what Preflight closes.

## Profiles

- **`pilot`** (default) — one scope, three to five anchors. Proves the loop closes quickly.
- **`thorough`** — multi-scope recovery in reviewed waves, coverage bounded by declared review capacity rather than a fixed count. For teams that have the time and want a well-rounded corpus before evaluating.
- **`audit`** — recovery only. No promotion, no branch, no pilot. Produces a coverage and cost report so the decision to commit to `thorough` is made on measurement rather than optimism.

The guardrails that do not relax in any profile: the human authority boundary, wave-bounded review, pre-registration of the pass/fail bar, and coordination between recovery scope and test-ticket selection.

## Where this Skill's data lives

- Pass/fail criteria — `.bearing/ledger/pass-fail-criteria.md`, written from a packaged template by `bearing init --pass-fail`. Not in this directory: a completed criteria document is repository content and would be destroyed on plugin update.
- Pilot run rows — `.bearing/ledger/cost.jsonl`.
- Onboarding state — `.bearing/runs/onboarding.json`, so a resumed session knows which step it is on.

`references/pilot-metrics.md` here documents what the four metrics mean and why token count is never reportable on its own.

## Maintenance model

`subagents/onboarding-coordinator.md` is canonical; runtime adapters are generated by `bearing render`.
