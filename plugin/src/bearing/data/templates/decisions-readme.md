# Decision Records

Authoritative architectural decisions for this repository. Numbered, sequential, and binding subject to each record's `Status`.

This directory is the answer to "why is it built this way?" If the answer is not here, it is not yet a decision — it is a preference someone holds.

## Reading order for an agent

1. **`{{index_file}}`** first. It is compact and tells you which records bear on the task at hand.
2. The specific record whose trigger matches. Only then, and only the ones that match.

That order is the point. Loading every record on every task is what makes documentation expensive enough to skip.

## Structure

- `NNNN-kebab-title.md` or `ADR-NNNN-kebab-title.md` — one decision per file, numbered in the order accepted. Either form may live directly here or in category subdirectories such as `auth/` and `frontend/`.
- `{{index_file}}` — generated by `bearing index`. Do not hand-edit.
- `{{shadow_dir}}/` — machine-inferred candidates. **Not authoritative.** See its README.

Category directories organize the corpus; they do not create separate ADR
namespaces. IDs and numbers must remain unique across the entire tree, numbers
are never reused, and superseded records are retained. `bearing index`, `lint`,
`context`, `verify`, and `assessment` all traverse the tree recursively while
excluding `{{shadow_dir}}/`.

## Front matter

Each record carries the metadata that lets it be indexed and enforced:

```yaml
---
id: ADR-0007
status: Accepted            # Proposed | Accepted | Deprecated | Superseded
eocr_function: Contract     # Entry | Operations | Contract | Rationale
trigger: adding a new payment provider integration
scope: src/payments/**
---
```

`trigger` is the field that does the most work, and the one most often written badly. It should describe *the situation in which an agent needs this record*, not what the record contains. "Adding a new payment provider integration" is useful. "Payment architecture" is not, because nothing an agent is doing ever matches it.

MADR-style `* **Status:** Accepted` bullets are also read, so an existing corpus does not need rewriting before BEARING is useful. `bearing lint` reports which records are missing fields needed for a complete index entry.

## Lifecycle

A record is never edited into a new decision. Set the old one to `Superseded` with `superseded_by`, and write a new record. `bearing verify --evolve` fails on a `Superseded` record with no successor, because a dead end in the graph is worse than no record at all — it stops an agent without telling it where to go.

## Anchors

Code that depends on a decision carries an annotation:

```
@see ADR-0007
```

`bearing lint` verifies every anchor resolves, and that none point into `{{shadow_dir}}/`.

Every scan-recognized `@see ADR-NNNN` is a governing Anchor: it asserts that
the linked decision governs or explains the implementation carrying the
annotation. Use an ordinary prose link for related reading that does not make
that claim.
